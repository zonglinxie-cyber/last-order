# 柜台交易／订单游戏：玩家反馈取样研究

日期：2026-11-05。范围仅为 Good Pizza, Great Pizza（770810）、Dealer's Life 2（1343670）、Potion Craft（1210320）。

**研究者未亲玩这三款竞品。** 本文依据公开 Steam 评价，研究“玩家怎样描述重复、哪些变化受到肯定或排斥”，不是竞品机制实测，也不是总体民意调查。只新增此资料文件；不实现功能，不改已有文件，不提交、不推送、不更新公网，不读取 `.env`。

## 1. 先固定口径，再获取样本

### 1.1 预先确定的采样规则

在阅读任何样本前确定：每款英文、购买于 Steam、正负各最多 8 条，有帮助排序 `filter=all`，`filter_offtopic_activity=1`。补充固定 `day_range=365`、`num_per_page=8`、首屏 `cursor=*`。每个游戏／正负组合只取一个首屏，不翻页、不因内容不合意替换，不因不足 8 条扩大时间窗。

原计划 endpoint：

```text
GET https://store.steampowered.com/appreviews/{appid}
json=1
language=english
filter=all
day_range=365
review_type=positive 或 negative
purchase_type=steam
num_per_page=8
cursor=*
filter_offtopic_activity=1
```

**实际发生接口变更，不隐瞒口径差异：** 第一次请求披萨正评时，旧接口未返回 JSON；随后同参数诊断请求于 `2026-11-05T14:50:37Z` 完成，最终地址为 Steam 商店首页，HTTP 200、`text/html`，不是评价。此时尚未取得评价样本。

[Steam 旧接口官方文档](https://partner.steamgames.com/doc/store/getreviews)注明该接口已弃用；[官方迁移与参数说明](https://partner.steamgames.com/doc/webapi/IUserReviewsService)指定替代接口 `IUserReviewsService/GetAppReviews`。因此在读样本前宣布改用官方公开替代接口，保留筛选意图，不改采样游戏、数量、正负分层及时间窗。它不需要 API key。

实际 endpoint 与公共参数：

```text
GET https://api.steampowered.com/IUserReviewsService/GetAppReviews/v1/
query 参数：input_json=<以下 JSON 的 URL 编码>
```

```json
{
  "appid": 770810,
  "languages": ["english"],
  "filter": 0,
  "day_range": 365,
  "review_type": 1,
  "purchase_type": 0,
  "num_per_page": 8,
  "cursor": "*",
  "filter_offtopic_activity": true
}
```

其中：

- `appid` 分别为 `770810`、`1343670`、`1210320`。
- `filter=0` 是官方枚举 Helpful，对应旧版 `filter=all`，**不是按时间最新，也不是所有历史的简单有用票数榜**。
- `review_type=1/2` 分别对应正评／负评；`purchase_type=0` 对应 Steam 购买；布尔 `true` 对应旧版 `filter_offtopic_activity=1`。
- 新接口的 `use_review_quality` 未另行设置，按文档默认 `true`，会把低质量内容排后。不能声称排序与旧接口某个历史时点完全相同。
- 六组返回的 `day_range_used` 均为 `365`，没有观察到自动扩窗。
- 六组均为 HTTP 200；逐条检查 `language=english`、`steam_purchase=true`、正负标志与请求一致。
- 文档提示匿名返回可缓存至多 10 分钟。下列时间是请求完成时间，不是评论发表时间，也不保证服务器实时生成。

### 1.3 最小保存与单评永久链接限制

- API 完整对象只在请求进程内处理；未将原始 JSON 或完整评价库写入磁盘。用于阅读的输出只提取评价 ID、正负、游玩小时和评价正文，没有输出作者账号字段。
- 本文件仅保留必要的评价元数据、每条不足 80 英文词的原文短摘及中文分析，不保存用户名、SteamID、头像或个人主页地址。未把评论里的推广署名、链接或歧视性辱骂搬入资料。
- 表格统一使用**发表评价时的游玩小时**：`author.playtime_at_review / 60`，四舍五入到两位小数；不是当前累计时长，不等于有效游玩／完成进度。
- **未完成项：不含身份的官方单评永久链接未能核验。** 曾验证一个不含身份的候选地址，实际跳回社区首页，已舍弃，未把它充当出处。随后只为核验链接重复读取既有 G+ 首屏元数据，未重选样本；在内存中打开 G+01 的标准单评页，HTTP 200 且匹配原文，但 URL 含用户身份字段，因此没有保存。
- 下文的外部引用是**当时的采样 API 链接＋具体 recommendation ID**，不是单评永久链接。点击后可按 ID 查找；今后排名变化或评价删除后，首屏可能不再含该 ID。本文件提供短摘留痕，但不能冒充不可变网页快照。此限制意味着原定的“每条永久链接”取证目标未完整满足，不以假链接或身份字段换取表面完整。

## 2. 可据此说什么：机制主题、反例与推断

以下“原话证据”仅说明受访式评价中出现了该体验；“推断”是研究者解释，**不是已验证的因果关系**。各编号的原话、ID、正负和小时见第 4 节。

### 2.1 重复的一个具体来源：学会后，不再需要重新做决定

**原话证据：**

- [D+06／231145397][api-dp] 将问题明确写为 “linear growth and few options”；它仍然是好评。
- [D+05／232161233][api-dp] 写 “Same things to buy and sell”，既期待新东西，也肯定讨价还价、赚钱和拍卖。
- [P−06／219032468][api-pn] 说后期 “It doesn't feel like problem solving”，并把已经掌握的操作比作走路／开车。该文同时详细肯定前期学会新技巧的体验，不是从头否定制作机制。
- [P+07／233569256][api-pp] 描述熟客、熟悉效果及经济不再重要；仍推荐游戏，认为 56 小时后达到概念上限不一定是重大缺点。

**推断：** 对这几位玩家，“重复”不是单指订单数量少，而是已经掌握的解法持续适用，继续玩主要扩大数字或复现动作。因此“加顾客文案／商品皮肤”不能据此被视为已解决重复；但这些评论也不足以证明增加内容一定无效。

**反例／边界：** D+05 仍享受赚钱本身，P+07 接受有限生命周期。不能把“后期重复”推成“前期失败”或“所有玩家需要无限内容”。

### 2.2 受到肯定的变化：新解法、技能成长、交易悬念；不等于功能越多越好

**原话证据：**

- [P+07／233569256][api-pp] 肯定不同材料、研磨程度、路径、基底和组合可以到达同一效果；这是“同一目标、不同办法”的直接描述。
- [P+05／217843281][api-pp] 肯定 “charting new potion paths, refining techniques”，同时批评外围系统很少迫使自己重新思考。
- [D+03／214680003][api-dp] 喜欢压价、被顾客骗及买入物品可能是假货的循环；这支持至少一位玩家觉得交易不确定性有吸引力。
- [D+05／232161233][api-dp] 写 “The auctions are fun tho.” 但未解释为什么有趣，**不足以推断拍卖的哪项具体机制奏效**。

**推断：** 相比只增加名词，更值得测试的是“眼前条件变了，玩家需要比较不同解法”。这些评论提供方向，不提供本项目应使用的具体概率、策略数或平衡数值。

**反例：** [D+02／230414918][api-dp] 的主要快乐恰恰来自顾客接受夸张高价，未必来自复杂决策；更高难度、更多策略不是唯一乐趣。

### 2.3 伪变化：读谜语、补材料、追加手工，未必带来新判断

**原话证据：**

- [G+05／218269440][api-gp] 同时认可顾客表达方式独特，又抱怨谜语难解；配料越多，顾客越要全加，手工负担变重。
- [G+06／217119280][api-gp] 说数学题订单要去 YouTube 查；[G−04／213763594][api-gn] 抱怨订单含糊且问清楚还遭顾客无礼对待。
- [G+03／209224371][api-gp] 希望为学阅读的孩子提供不走时间的模式：阅读／理解速度与倒计时在此发生冲突。
- [P−01／226358771][api-pn] 不愿为顾客“最喜欢的材料”重做已有多瓶的药水；[P−02／209507638][api-pn] 抱怨同一种材料磨 15 次只为向左移动一点。
- [P−06／219032468][api-pn] 将某些禁用现成做法的限制称为容易解决、却迫使自己手工多做几分钟的麻烦。

**推断：** 如果玩家早知道答案，只因限制被迫读得更久、点得更多或重做一遍，这可能是工作量变化，不是决策变化。对话可以有趣，但“故意说不清＋惩罚澄清”有体验风险。

**重要反例：** G+05 认可诙谐表达，G+06 仍觉得上瘾。这里不是“禁止谜题”，而是应区分可推理的谜题、信息缺失、阅读负担和重复劳动。

**自动化的两面：** [P+07／233569256][api-pp] 明确肯定一键重制方便，又认为它移除了原本有趣的制作过程；而 P−01 反感被迫重做。由此只能提出待测方向：让已掌握流程更省事，同时让新单出现值得比较的新问题；不能简单主张全面自动化，或以取消自动化制造挑战。

### 2.4 拉长目标与随机等待，可能只有时长，没有获得感

**原话证据：**

- [G+07／215979933][api-gp] 抱怨 “manufactured real time waiting periods”，认为剧情被无意义真实时间等待拖住。
- [D−01／225245426][api-dn] 不满买到最好店铺后，又要攒出其五倍金额；这是玩家对目标设计的陈述，未经实测核验其精确数值。
- [P−05／229732500][api-pn] 说钱早就够了，进度却要等卖升级的商人随机出现，并抱怨缺少改变或扩展玩法的升级／事件。
- [P−03／214959703][api-pn] 认为终极目标解锁的物品，到能拿到时已经不需要了。

**推断：** 新章节或更大金额若没有新用途、可计划的下一步或玩法改变，可能被体验为延迟结束，而非成长。订单变化和长线升级需要分开验证，不能指望长目标自动拯救短循环。

**反例／边界：** [G+01／236909778][api-gp] 抱怨赚钱慢，却仍喜欢制作和种植；[P+06／215532795][api-pp] 认可全部解锁前的内容。这里没有证据给出“升级应在第几单发生”的通用答案。

### 2.5 重复不必消灭；压力与胜负需要看玩家目标

**原话证据：**

- [P+02／220394408][api-pp] 明说这类重复是自己喜欢的；[P+04／232622679][api-pp] 写 “i love doing tasks”。
- [P+08／229993564][api-pp] 肯定没有时间压力、可自由试验；[G+02／210021971][api-gp] 把享受过程、放松与冲活动名次区分开。
- 与之相反，[P−04／236584653][api-pn] 抱怨过于轻松、没有失败状态，却同样反对用刷次数冒充难度。
- [D−02／230979584][api-dn] 因最贵两件物品被偷而弃玩，明确表示现实压力已经够多。

**推断：** “增加风险／失败／倒计时”不能被当作统一解法；“更多重复＝更差”也不成立。研究中至少应区分追求经营胜负、追求轻松劳动、追求探索解法的动机，而非把它们混成一个满意度数字。

**限制：** 上述并非统计聚类，不知道三类人群的占比，不能据此定产品受众或证明必须做多种模式。

### 2.6 顾客关系、回访和故事：有诉求与正例，但不足以证明留存增益

**原话证据：**

- [D+08／211543312][api-dp]（发表时 83.53 小时）在高度认可游戏的同时，希望能与顾客建立关系。
- [D−01／225245426][api-dn] 也抱怨没有顾客关系，交易一直只剩买卖。
- [P−01／226358771][api-pn] 喜欢跟完顾客的小支线，却不满没有最终故事收束。
- [P−06／219032468][api-pn] 对反复回来的彩蛋角色说 “it's neat ONCE”；[P+03／214869782][api-pp] 则靠自己扮演邪恶女巫给完成后的游戏加趣味。

**推断：** 让顾客“记得上次交易、下次因此变化”值得测试，可能比只有新台词更能产生连续性。但评论中的“希望有关系”是愿望，不是“加入关系系统一定延长寿命”的证据；玩家自发角色扮演也不是已验证的内置分支系统。

## 3. 不该混进玩法结论的噪音，以及采样限制

1. **披萨负评被商业模式／移植预期显著占据。** 本样本 G−01、03、05、06、07、08 共 6 条主要谈付费买断后仍有内购、免费手机版与 PC 版价值预期，没有提供可分析的核心交易重复机制。它们不该被计成“6 人认为订单无聊”。G−02、04 则同时涉及玩法、控制和收费，需要拆开读。付费信任问题真实重要，但与本任务的重复机制是不同问题。
2. **不把评论中的指控当产品事实。** 评论对披萨内购是否影响胜负说法不一：G+02、G−02 将其与活动／进度联系，G+07 认为购买主要是装饰。本文未核实付费体系，也不采信 G−07 的平台政策违法指控。
3. **低信息量评价保留，不换成“好用证据”。** D+01 是模板式勾选和一句笑话；D+07 泛泛肯定消遣；D−04 只说重复；D−05 只比较前作；D−06 没有理由。这些可以说明态度，不能支持具体机制归因。
4. **辱骂不是机制证据。** D−03 含歧视性辱骂，未保存该部分，仅保留“开头好、后面无聊”和物品价值的中性片段；不因此将其粗暴语气升级为更强证据。
5. **正负标志不是段落情绪。** G+04、D+04／05／06、P+01／05／07 都是正评且批评重复；不能只读负评寻找问题，也不能把好评当作无条件赞同。
6. **是目的性、有帮助排序、正负配额样本，不是随机样本。** 24 正／22 负是采样结果，不是好评率；不报总体百分比，不比较三款游戏谁“更重复”。英文 Steam 购买者也不能代表中文手机玩家或免费用户。
7. **窗口与排序有选择偏差。** 固定一年窗口；Helpful 与默认质量排序偏向会写、被认可、可见的意见，过滤离题活动不等于没有笑话、推广或收费争议。未按时长／版本／更新日期再分层，不保证所有评论对应同一版本。
8. **自述不等于行为日志。** 游玩小时可能含挂机；评价时长不等于通关时间；觉得“随机”不证明底层概率；声称弃玩不证明后来没有回来。没有实验、留存数据或同行为对照，不能从这些评价推导因果强度。
9. **没有证据的部分明确留空。** 不知道最优商品数、顾客数、订单长度、新机制解锁间隔、手机触控体验、付费转化或一年留存；也不知道 24 顾客／72 来意本身是否不足。
10. **引用可追踪性不完美。** API 样本有明确 ID 和取得时间，但没有保存身份型单评 URL，也没有永久网页快照；首屏会变化。不要把此文包装成可完整重放的总体数据库。

## 5. 对本项目的可测建议：只列研究假设，不实现

项目现状采用任务说明：**七天争柜已有 24 顾客、72 来意，交易仍主要是问需求／预算／试用／选 6 商品。** 本研究没有审计代码，不把这段描述扩写为未核验的系统现状。

下列均为基于上述样本的**设计推断**，不是竞品已经验证有效的方案。数字若出现在试验条件中，应另行预注册为实验设计，不能冒称玩家调研推导出的最优值。

| 优先研究问题 | 可做的对照（未来研究，不是本次实现） | 观察／记录什么 | 什么结果会推翻假设 | 依据 |
| --- | --- | --- | --- | --- |
| 顾客变多，是否真的改变交易决策？ | 保持 6 商品、同一批顾客与相当时长；对比“只换来意文案”与“条件改变后确实存在不同取舍”。条件示例可用期限、交付方式、售后承诺，但这些是本项目假设，不是三款游戏已证实方案。 | 玩家能否说明为何换了方案；问询与选品路径是否不再固定；满意度／想再接一单；同策略的收益差异。不能只数点击分支。 | 路径变多但玩家理由没变、理解成本升高或更不想继续；或始终有一个最优解。 | D+05／06、P+05／07、P−06 |

**建议先研究的顺序（研究者判断）：** 先验证“同样 6 商品下，订单能否产生不同且可解释的取舍”，再验证顾客回访是否延续这些选择；不要先扩大顾客／商品总量来掩盖固定流程。理由是样本对“解法固定、附加劳动、拉长目标”的具体描述，比对“理想内容数量”的证据更充分，而后者实际上没有可用数值证据。

**验证纪律：** 测试条件、观察指标与停止标准应在开测前确定；安排早期熟悉与掌握后的重复阶段，避免只测第一单的新鲜感。路径差异、口头喜好与真实持续游玩分别记录。若没有后续行为跟踪，报告只能说“当次测试更愿意继续”，不能说“已提升长线留存”。

## 6. 给主线程的压缩结论

- 取样 **46 条**，不是 48 条：披萨 8+8、当铺 8+6、炼金 8+8；保持原定筛选，不补挑。
- 最清晰的重复线索：**掌握后不再重新决策、内容只改表面／金额、进度靠额外操作和等待拖长**。重点读 [D+06／231145397][api-dp]、[P−05／229732500][api-pn]、[P−06／219032468][api-pn]。
- 变化也会失败：含糊读单、全配料手工、为指定材料重做已有货，都有人反感。重点读 [G+05／218269440][api-gp]、[P−01／226358771][api-pn]。
- 反例必须保留：有人喜欢熟悉劳动与无时间压力，有人嫌没有失败；**不要直接等同“更难／更随机／更多步骤＝更好玩”**。见 [P+08／229993564][api-pp]、[P−04／236584653][api-pn]、[D−02／230979584][api-dn]。
- 顾客关系有明确愿望，尚无效果证据；先测试它能否改变回访交易，而不是宣称加故事就能长线留存。见 [D+08／211543312][api-dp] 与 [D−01／225245426][api-dn]。
- **未亲玩竞品；未改代码、未部署。** 旧接口已弃用，实际使用官方迁移接口；不含身份的单评永久链接未能核验，因此只提供 API 采样出处＋ID，不能冒称全部满足永久链接要求。
