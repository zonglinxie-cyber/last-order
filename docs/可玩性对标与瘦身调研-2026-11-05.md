# 人情场：可玩性对标与瘦身调研

日期：2026-11-05。性质：**当前实现审计 + 公开资料调研 + 待验证的方向建议**，不是已执行的删改方案。

## 先说结论

**值得瘦身，但首要任务不是减少代码行数，而是减少玩家需要同时理解的目标，让已有系统共同服务一次有意思的销售判断。**

现在最值得保留的不是“系统很多”，而是这个组合：

> **读懂一个人 → 决定这一单怎么卖 → 留下人情或代价 → 下次她带着这个结果回来；与此同时，对面正在抢你的机会。**

建议定位：**手机端、熟客驱动的轻策略销售游戏**。有明确的周挑战，有可复盘的输赢，有值得记住的人；不继续同时扩大社交沙盘、剧情连载、年度职业经营三种规模。

优先级：**目标与奖励一致性 → 判断与后果 → 手机信息层级 → 交付体积 → 开发流程精简**。必要的发布可靠性问题可以与玩法试验并行处理。

## 一、调研边界

- 检查了当前 `dynamic-counter-prototype/src/world/`、运行时与发布脚本、测试组织及设计记录，抽查具体规则，不把旧提案当已实现功能。
- 获取了七款游戏的官方站／官方商店公开资料。它们是机制参照，不都是个人开发，也不都是免费小游戏；不能把 PC、手机和微信小游戏的商业化口径混用。
- 对本项目运行了构建和两个默认口径的手机首单 E2E；查看本轮生成的接待／成交截图。
- **没有真人可用性访谈、次日留存、商业收入、低端真机帧率或弱网加载数据。** 本报告不能据此断言玩家流失比例，也不提供伪造的竞品留存率。
- 没有修改游戏、存档、运行时锁或测试要求；不做重写和整批删除。

## 二、同类作品怎样做可玩性

表中“循环”由公开页面支持；“借鉴”是本次设计分析，不代表开发者原话，也不是其商业成功的因果证明。

| 参照 | 核心循环与变化来源 | 人情场应该借什么 | 不应该照搬什么 |
|---|---|---|---|
| **可口的披萨，美味的披萨** | 听订单、制作、交付、经营；谜语式订单、熟客、邻店竞争与章节改变情境 | 一个柜台也能有归属感；认出熟客、听懂话，应直接帮助这一单 | 不照搬重复制作劳动，也不照搬多年积累的活动与装饰量 |
| **Dealer’s Life 2** | 判断商品与顾客、讨价还价、积累资金；不同商品、顾客、事件与骗局 | **交易本身是主要挑战**，外围系统帮助下一次交易 | 不同时扩出拍卖、投资、海量商品、员工经营等新工程 |
| **Papers, Please** | 检查信息、对照规则、必要时追问／搜查，再决定如何处置来人 | 少量证据支撑有分量的判断；人物故事发生在工作动作里面 | 不把销售变成查表找错考试，更不能让每单只有一个标准答案 |
| **Reigns** | 左右滑动决策、平衡四方；后续事件、多代统治、目标解锁 | 固定少量操作，靠后果和再次相遇增加深度 | 不把销售压成看不懂后果的盲选二选一 |
| **Potion Craft** | 理解顾客问题、制作药剂、交易；配方实验、多种解法及关系变化 | 卖的是解决方案；同一个问题可以有不同代价的答案 | 不另造复杂制作小游戏，抢走识人和成交的中心位置 |
| **Balatro** | 出牌／弃牌、组合效果、达到盲注门槛；牌组、Joker、Boss 与难度改变打法 | 清晰过关线、局内成长、少量规则之间的组合；“下次换一种办法” | 不把人变成倍率材料，不照着扩一套无关卡牌系统 |
| **Luck be a Landlord** | 转动获得收入、选择符号／道具、应付租金；效果相互作用改变收益 | 减少重复操作，让之前的选择产生可解释的后效 | 不让成交靠随机开奖；销售游戏要保留判断的主导权 |

### 共同点不是“内容少”，而是“基础动作稳定”

1. **玩家很快知道现在要干什么。** 后续增加的是这个动作的情境，而不是不断增加必须学习的菜单。
2. **反馈能解释选择。** 玩家能把结果归因于自己的决定，才会形成能力感。
3. **重复中有变化。** 同样操作，顾客、约束、组合或旧承诺不同，答案随之改变。
4. **有短周期收束。** 一天、一关、一段挑战能让人明确知道赢了什么，输了以后要改什么。
5. **长期内容服务核心循环。** 并非每款都无限重玩；高质量有限流程也成立。不能把“希望玩一年”直接翻译成“先做几年剧情”。

### 手机小店与付费独立游戏要分开参考

《披萨》移动商店显示免费下载、内购及广告；Steam 版本为付费且页面明确无广告。后五款参照中的买断／构筑思路不能证明免费小程序的获客和商业化效果。

本项目当前是可安装的 Web/PWA；本轮应先回答“第一周愿不愿意玩、愿不愿意重玩”。如果以后确定进入微信小游戏或广告变现市场，再单独研究平台包体、启动、广告频率和付费，不把商业化系统预先塞进玩法。

## 三、当前项目的实测快照

### 1. 内容和工程规模

| 项目 | 当前读数 | 应如何理解 |
|---|---:|---|
| `PEOPLE` / 顾客 | 43 / 32 | 人物总数不是单屏同时出现人数 |
| `STORYLETS` | 371 张 | 内容资产，不等于 371 个独立玩法 |
| 货架 | 12 支 | 先检查每支是否创造选择，不按数量直接删 |
| `src/` 代码物理行 | 32,893 | 含空行与注释，不是可执行指令数 |
| `src/world/content/` 物理行 | 18,876，约占 57.4% | 大半源码是人物／剧情数据，不能全称为架构垃圾 |
| 测试物理行 | 19,190 | 统计排除两个手工 probe；测试不进入游戏主包 |

规模统计排除 `node_modules`、`dist`、`tmp`、审计截图等生成／临时产物。没有找到第二套仍运行的旧游戏入口；当前 `App` 进入的是同一个 `WorldGame`。

### 2. 本轮生产构建

| 项目 | 读数 |
|---|---:|
| 客户端目录 | 104 个文件，9,827,145 B，约 **9.83 MB** |
| 主 JS | **1,314.68 kB**，构建器估算 gzip **373.28 kB** |
| 主 CSS | 74.18 kB，gzip 15.07 kB |
| 中文字体 600 / 700 两份 | **3,084,540 B**，约 3.08 MB |
| `assets/game/` 资源 | 4,634,592 B，约 4.63 MB |
| SW 预缓存 | **103 个文件**，除 SW 自己外几乎整个客户端 |

这里 MB 为十进制。目录大小不等于压缩后的网络传输量，SW 安装预缓存也不等于全部阻塞首屏。**没有测出“手机已经卡顿”**；但对即时进入的网页小游戏，字体和预缓存是明确的优化对象。

构建提示主 chunk 超过 500 kB；这是优化提示，不是构建失败。只拆文件、不改变静态导入与预缓存策略，也不一定减少总下载。

### 3. 首单不是完全没打磨

本轮两个真实开场用例通过，覆盖 320×568 和 390×844：直接接客、探问中断恢复、成交复盘、首张剧情只出现一次。

现有优点应保留：

- 新手先接待沈薇，不再先被故事卡挡住。
- “看／问／试”、已知信息、成交原因与“下一单用得上的事”已经存在。
- 查看不立即扣精力，真正开始接待才付费；中断后能续谈。
- 对手意图、邀请、熟人搭话、周末单的回应已有落地，不需要另起炉灶。

但“按钮可点”和“知道为什么点”是两种验收。320 宽截图中，人物观察区只能露出一部分，追问在下方；390 宽首屏也同时包含精力、耐心、预算、件数、两步标签、已知需求、对白和探问区。**这是信息层级压力，不是已证明的点击故障。**

## 四、最重要的短板

### A. 几套“成功”没有完全接起来

周结算在业绩、客情、守客中取最高星数；职业评估则仍要求一年有 2／3 季销售额赢对面。职业考核里的“客情”又主要是苏蔓／唐可认可，并非周目标中的顾客照应。

- 证据：`src/world/target.ts:243–253`；`src/world/career.ts:70–77,172–205`。
- 风险：玩家明明用客情过关，却发现另一套系统不把它当主要成功；需要学习多个“客情”的不同口径。
- 取舍建议：**先统一成功含义，再增加达成方法。** 原型中试验“一个可见主目标，客情与守客作为实现它的策略”；不是单纯藏起仍然互相矛盾的考核数字。
- 边界：并行多目标不天然错误。若真人明确喜欢非销售路线，可以保留，但必须把它的奖励接到后续成长，而不是只在周结算加一颗星。

### B. 部分配货提示在替玩家做隐藏信息推理

`pairPartners()` 直接读取完整需求、底线、预算和件数，筛出真正能配成的组合。界面显示“能搭配”、候选与“最省组合”，其中这些候选显示并没有统一受“已经问清”限制；只有一条提示文字有这个限制。

- 证据：`src/world/shelf.ts:205–218`；`src/world/ui/ConsultPanel.tsx:55–62,158–175`。
- 风险：本来应该“搜集证据后判断”，局部变成“跟着系统标记挑”。这是规则信息边界问题，不是删除所有帮助提示的理由。
- 建议：事前提示只依据已知信息；未知写未知，试用与事后解释保留。搭配界面本身也要按已知信息设计，不能只隐藏文案而继续用隐藏数据过滤选项。

另外，问偏或看不到新信息通常不消耗耐心（`consult.ts:250–302`）。它降低新手挫败，也可能鼓励逐项点完。是否调整要看实际操作记录，不能直接宣布它是坏设计，更不应一上来把所有试错改成惩罚。

### C. 文字里的牺牲，未必收取真实代价

抽查梅女士人生卡，“把下午排给她一个人”主要增加好感、柜位与关系，并未真正占用下午或精力；提醒后面还有客人反而扣分。

- 证据：`src/world/content/storylets-life.ts:176–220`。
- 风险：玩家可能学到“选体贴的话拿奖励”，而不是“人情与业绩如何取舍”。这些选项有关系门槛，不一定同时可选；这里证明的是承诺没有对应机会成本，不是证明存在全局万能善意路线，也不能推成所有故事卡都如此。
- 建议：不急着继续写分支，先挑 5–10 张关键卡，把承诺接到精力、到访时机、另一位顾客或下一次订单上。无需强迫恶意选项与善意选项一样强，但不同善意选择可以有不同成本。

### D. “维护熟客”的计数口径不一致

周客情要在同一周不同日亲自照应两次，而购买间隔为十天；仅靠对症成交无法在一周内完成两次。长期流失却读取 `served:`，送样等维护不等同于接待；`settleServe()` 又在处理拒绝、近期购买等分支前记录接待并清除流失。

- 证据：`src/world/purchases.ts:3–18`；`src/world/engine.ts:1622–1650,1888–1896`。
- 风险：玩家需要记规则计数器，而不是凭直觉理解“我有好好照应她”。拒绝成交也可记接待，不意味着一定是 bug，但与“她没在你这里开过单”的表现并不完全一致。
- 建议：先定义什么是“有意义的一次照应”，统一或明确区分关系维护与购买记录；再决定要不要排班。别为了让固定模拟脚本的客情从 0 变正数，立刻再造系统。

微信回购还有一个待测问题：自动卖一支也会启动购买冷却，可能占掉更大订单的机会。它是潜在负激励，**尚未做收益对照，不能断言自动回购整体有害**。

### E. 长线变化来得晚，内容长度不等于重玩深度

当前已有年景、人生变化和第 4 级三个职业分支，不能说这些都没做。人生阶段也确实影响预算、用量和需求，不是纯文字皮肤。

但按当前四季一年、28 天一季、每天四时段推算：最早首次晋级要经历 **448 个时段**，第 4 级分支要经历 **1,344 个时段**。这是规则长度，不是真人游玩分钟数。

- 证据：`src/world/career.ts:114–146`、`src/world/years.ts`、`src/world/types.ts`。
- 风险：比较显著的玩法身份变化在很后面，而前面重复的是类似接待。
- 建议：先证明一个星期值得重玩；长线解锁优先改变“这次怎么做决定”，不只是多几格数值、更长年表。先冻结新增人物、人生续章、职业分支和传承。

### F. 模拟器的“结果多”，不是玩家的“选择有意义”

`world-sim` 的部分销售策略直接读取完整需求；剧情选项为随机；签名主要是盟友／仇人组合。`consult-sim` 虽有有限信息口径，却明确不包含剧情和委托。

- 证据：`tests/world-sim.ts:57–76,344–359,444–451,924–936`；`tests/consult-sim.ts:1–10`。
- 签名不同可能来自随机结果；几种固定脚本没有通吃，不排除真人混合策略存在优势。
- **保留这些回归**来验证可达性与数值分布，但增加真人指标：能否说明失败原因、是否因局势改变计划、是否自发想重试。
- 本轮没有重跑长模拟；历史读数只用于理解设计过程，不冒充本轮结果。

## 五、“不必要的代码拦截审查”到底有哪些

### 应改进，但不是线上审核的部分

| 现状 | 判断 | 建议 |
|---|---|---|
| `predev` / `prebuild` 对 28 个运行时文件比对 SHA-256 | 任意字节改动会拦开发／构建；是修改确认，不是行为正确性证明，也不是玩家端审查 | 保留约定，先修正要求“恢复运行时”的过时提示；开发启动是否改提醒另行决定，发布保留有效验证 |
| 测试断言源码必须含某种 `useMemo` 或展开表达式 | 等价重构也可能触发；这是可以减少的实现耦合 | 用安全区、全屏、行为契约代替精确源码形状 |
| 剧情措辞词表／代词扫描 | 是本地编辑质量规则，不是在线内容过滤服务 | 按内容变化运行，设置明确例外；不能把文案 lint 当玩法验收 |
| 一个 `npm test` 串起规则、构建、完整 E2E、发布测试 | 作为全量命令合理，但不适合每次小修改都执行 | 拆日常快检、按模块回归、发布全检；不减重要覆盖 |
| Pages CI 主要执行构建 | 发布自动验证反而偏薄，不是所有环节都过审查 | 将必要的短行为测试放进发布链，长模拟定期或规则／内容改动后执行 |

证据：`package.json:9–19`、`scripts/check-mobile-runtime.mjs:12–30`、`tests/mobile-chrome.test.ts:26–47`、`tests/world-lint.test.ts`、`.github/workflows/pages.yml`。

**这些测试、哈希锁和 lint 不进浏览器主 JS。删掉它们，不会解决 3 MB 中文字体或全量预缓存的问题。** 当前锁通过，没有正在发生的锁阻塞。

### 必须保留保障的部分

- 存档校验、已发布格式兼容与迁移、刷新／后台恢复。
- 触摸拖动后的防误点、滚动、键盘与安全区处理。
- 引擎执行入口的精力、对象、购买条件检查，避免绕过 UI 后出现非法状态。
- 对不存在资源、非 HTML 请求的正确响应；不能用 SPA 回退掩盖错误。
- 核心规则、内容可达性和真机流程的行为测试。

可重构实现、调整频率，但不能为了“瘦”删除这些行为保障。现有项目规则要求的运行时锁更新流程仍然有效。

## 六、工程上真正值得瘦的地方

1. **字体与资源加载。** 优先比较系统字体、一种中文字重、分片／子集字体的效果；必须覆盖剧情与新增文本，不能只截首屏字集。图片先分析尺寸和使用场景，不直接删除人物美术。
2. **桌面预览与真机边界。** 外框、假键盘等资源即使真机不渲染仍被全量预缓存。将预览专用组件／资源从产品初始加载链分开；当前依赖都有引用，不能凭包名整包删除。
3. **PWA 更新可靠性。** 目前缓存版本从入口 `index-*` 哈希取得。同名 public 资源内容变化、入口哈希不变时，生成的 SW 可能不变，旧安装用户继续读旧缓存。应把资源内容修订纳入版本，并补真实更新测试。此项是代码确认的失效条件，本轮未浏览器复现。
4. **旧开发 SW 与测试。** `public/sw.js` 仍列已不存在的 PNG；生产构建会覆盖它，开发也不自动注册，不能据此说生产离线已坏。应收敛到实际生成逻辑，测试验证资源、安装、离线和更新，而非旧缓存名。
5. **职责耦合。** `engine ↔ requests`、`engine ↔ exchanges` 有值依赖循环，注释依赖“不在顶层调用”保证加载；`WorldGame.tsx` 同时承担存档、会话、引导和布局。优先提取共享状态操作、存档与会话边界，而非机械切大文件。
6. **部署包装。** Pages 只消费客户端，但通用 build 也要求 Sites 包装输入。可把客户端构建与特定部署包装分开；收益是减少无关阻塞，不是显著减包。
7. **文档与临时材料。** 设计文档混有旧现状和多年次序的历史追加，容易把历史数据当当前真相。后续应保留一个短的当前规则索引，历史只追加不覆盖；临时 probe／截图先做引用与跟踪状态清单，不碰用户已有未跟踪工作。

## 七、具体保留、收起、冻结什么

| 处理 | 对象 | 原因 |
|---|---|---|
| **强化核心** | 看／问／试、预算与耐心、配货、成交复盘 | 玩家“我会卖了”的能力感来自这里 |
| **强化核心** | 客情笔记、预约、熟人搭话、牵线 | 人情应该变成可主动使用的机会，而非只涨好感 |
| **强化核心** | 对手公开意图、争客、周末最后一单与回访 | 现成的准备—执行—输赢—后果闭环 |
| **保留但降噪** | 关系网、档案、记忆、柜位、台账 | 有价值，但不是每单都要展开的作业 |
| **情境化出现** | 保密、传话、介绍、调解等动作 | 有具体人物／事件理由才突出，不要求日常逐个刷收益 |
| **进阶再开** | 年景、自选加难、复杂职业考核 | 不让首周同时解释多层规则；不是立即删除底层状态 |
| **暂冻新增** | 排班、新人物、新人生续章、新职业分支、传承 | 先证明已有选择值得做；尤其不以修模拟器指标为加系统理由 |
| **清理候选** | 失真开发 SW、脆弱源码匹配、预览耦合、重复真源 | 有可说明的维护／交付收益，且能用行为测试验收 |
| **不直接删除** | 现有人物与剧情数据、12 支货架、存档兼容 | 缩减首周呈现不等于毁掉资产；移除货架可能破坏已有顾客解法 |

## 八、推荐方向与验证路线

### 方向选择

- **推荐：熟客驱动的轻策略销售。** 一个柜台／楼层，小步判断，熟客带来生意与矛盾，周末有一场值得争的关键单。最能利用已有销售、人物与对手资产。
- **备选：叙事小店。** 如果试玩发现大家主要想认识这些人，就降低业绩考核压力，承认是有限章节体验；不要一面要求舒适叙事、一面叠高强度全年考卷。
- **暂不推荐：无尽经营／多职位沙盘。** 需要更深的经济、自动化和管理循环，开发与平衡成本高；目前继续扩展会放大现有目标不一致。

### 第一轮：只证明一个星期，别新造一个模式

沿现有唯一入口，选第一周做可回退原型；先不删 28 天季制和旧存档，也不再维护一个分叉引擎。

- 从现有人物中让 **6–8 位成为首周重点熟面孔**，不是把全体永久砍成 8 人。
- 首次教学聚焦 **4–6 支有区别的货**；只有确认这些货覆盖当周顾客合理解法后才能限制范围，否则先只调整展示与教学顺序。
- 屏幕明确一个当前主目标；人情和守客的收益应落到下一笔机会、对手损益或结局，而非另加进度条。
- 每次决定突出“现在最值得考虑的两三件事”，其他动作在有情境时出现。不是把所有系统强行改成二选一。
- 单次接待 **30–90 秒**、一次手机会话 **3–5 分钟可停**作为待测节奏目标，不是现有实测时长；七天挑战可分多次会话完成。
- 用少量关键选择验证“多赚这单／为另一位留精力／兑现承诺”的差别。先使用已有资源，不新增货币或复杂排班。

### 第二轮：真人判断是否变好玩

招募约 8–12 名没看过说明的目标玩家，用固定种子对照当前版和精简原型，记录两版顺序，减少先玩哪版的影响。小样本用于找问题，不用于宣布统计显著或市场留存达标。

建议观测：

1. 从开场到第一笔成交：时间、点击／滚动次数、卡住位置；将读剧情和无意义找按钮分开。
2. 能否说清“这单为什么成功／失败”“本周怎样算赢”。
3. 是否由于预算、精力、对手意图或旧承诺而真正改过计划。
4. 能否记住两三个顾客与自己做过的事，而非只记得数值。
5. 一周结束后，是否**自发**想重试；想换什么办法，而不是在主持人提示后答应。
6. 隔天是否主动回来。首次试玩意愿与实际 D1 分开统计，样本不足则只报告人数，不推断普遍留存。

可预先约定内部试验门槛，例如“多数新玩家无需解释完成首单，并能复述原因”；具体阈值要在测试前定。若只减少按钮但玩家仍说不出判断依据，瘦身没有成功。

### 第三轮：工程精简与回归

- 下载／发布线：字体 → 预览资源边界 → 缓存修订 → 弱网与离线验证。
- 开发线：快速命令／按模块回归 → 源码形状测试改行为契约 → 存档和会话职责拆分。
- 每次减少系统都记录被替代的玩家价值，更新调用、测试和文档；不只删除检查让它变绿。
- 改规则／内容后仍遵守项目要求，跑规则测试、模拟器并复核签名与打法分布；同时使用真人验证，不以机器人读数替代。

**不以“少了多少行”为验收。验收的是：玩家更快做有意义的决定、输赢更可解释、下次愿意换一种办法；同时首屏下载和改动验证成本确实降低。**
