## 追加：半脸上妆（2026-09-24 · 可选的一步，买的是信息不是钱）

手背试色看不出来的那件事，原来在规则里没有出口：她没说出口的诉求只能靠那三个固定问题问出来，问完就到底了。新增 `faceTrialService` / `faceTrialReveal` / `FACE_TRIAL_MINUTES = 2`：试用之后可以主动提出在她半边脸上上妆，多占两分钟，露出她「最在意却还没说出口」的那一条诉求（权重最高的一条未知诉求）。两个 UI 都调同一个 `faceTrialReveal`，不各写一份。

代价与边界（全部由规则用例量出来，不是写进断言的期望值）：

- 钱不变。同一位顾客，上脸上不上脸成交额一分不差（`assert.equal(seen.campaign.sales, blind.campaign.sales)`）；这一步买的是「你知道」，不是「你多卖」。
- 时间从队伍另一头扣。`spendAttention` 走原路，手机版顶部那句「梅女士 4/8 → 2/8」就是这一笔；沙盘 `.shift-clock` 精确 +2 分钟。
- 明知故犯另算。上脸看过、知道不合适还强推，信任 −4、台账 −4，历史多一行「她照着镜子看过这半张脸，还是买了」，成交文案多一句「她知道不合适，你也知道」；营业额照收。
- 一支只能上一次脸；换一支产品等于重新上脸，但她说出口的那条不会忘掉（`faceTrialRevealed` 保留、`faceTrialled` 复位）。
- 存档新增两个字段，旧存档缺字段按未上脸处理；`faceTrialled` 非布尔、`faceTrialRevealed` 不是已知诉求时整条存档拒收。

全柜十位客人都量过一遍：每一位都能在试用后再上脸露出至少一条未知诉求（`shen/mei/zhao/anjie/returning/duan/zhou2 → steady`，`xiaoyu/zhou → correct`，`anjie2 → correct`），不是只给沈薇做的演示关卡。

## 追加：去面板感第二轮——体力、记录本、进度条（2026-09-24）

上一轮列下的三个裸数字这一轮全部收掉，另外补上一个真正的规则缺口：`evidence`（五天留痕）从写进存档以来没有任何一条规则读过它，「五天记录」一直是装饰。

改了什么：

- 体力念成一句：`energyWord()` + `consultsLeft()`，一格按实测最贵的一单算（`ENERGY_PER_CONSULT = 24`；干净一单实测 17，被陆遥打断那一单 24）。沙盘栏 `体力 62 / 100`、手机版结果页 `剩余体力 62`、现场那行 `剩余体力 62 · 低于 18 时不能新开接待`、dock 里额外的「体力见底，接不了新人」全部换成同一句「还站得住，能再接 4 位」。值班手册里那句写死的「体力低于 18」改成读 `ENERGY_LOCK`。
- 记录本念成一句：`evidenceWord()`（摊得开 / 没几行 / 空着），分界线只有 `RECORDS_MIN = 4`。手机版今日账单原来的「证据 3」换成这句。写这一节的时侯发现沙盘栏位根本没提过本子（`src/` 里 `evidence` 出现 0 次），玩家要到第 5 晚才第一次知道有这本账——补上 `.rail-records`「记录本 空着 / 没几行 / 摊得开」，和第 5 晚问的是同一个 `evidenceWord`、同一条线。
- 留痕第一次有读者：第 5 晚 `argue-records` 由本子决定落点——摊得开 +10 柜位点、挂 `counter-argued-records`、判词「柜位留到季度末」；空着只 +3、不挂旗、判词仍是「撤柜评估已经写上去」。判词认旗不认分数，所以空本子摊开不能被骗成「留到季度末」。事件正文和选项说明先把「摊开来没几行」讲出来，不让人盲选；她没看完的那两页也不再算新留痕（只有摊得开才 +2），否则今日账单会反过来打脸。

## P10 · 楼层上第二个当场付的动作：迎上去（一支小样换她不走）

## P12 · 一周的货是有限的：配货、断货、两条调货出路

为什么先动这一处：接了十几轮，柜台里唯一无限的东西是货。清洁路线整周要吃 11 支柔焦，而规则里根本没有"支数"这个概念——`unitsWanted` 只看她说过几句、预算多少、用量上限。"品类结构考核"那一条 P9/P10 都记着"等有了多一位顾客进店的杠杆再回来"，其实缺的是配货这一头：先有抽屉，才谈得上抽屉里剩什么。

### 规则（只在 `campaign.ts`）

- `WEEK_ALLOCATION` = 柔焦 10 / 持妆 4 / 修护 7，是整周的硬上限；`stock` 进存档，`SAVE_VERSION` 4 → 5。`parseCampaign` 要求每支是 `0 … 配货 + TRANSFER_UNITS` 的整数，缺字段或类型不对整份拒收，不做 v4 数字到 v5 账本的合并。
- 件数被削两道：她自己说过的上限、抽屉里的支数。`unitsWanted` / `forcedUnits` 多一个 `left` 参数，`orderQuote` 与 `resolveSale` 读同一个 `left`——报价单说得出几件，入账就是几件（`playCustomer` 里 `units` / `total` / `minutes` 三条 `assert.equal` 守着，模拟器每次成交都核）。
- 断货不算判断错误：`resolveSale` 在开不出来时不扣信任、不动台账，旗子写 `served:<id>:out-of-stock`，成交卡说"没买成"。被抽屉削掉的那几件不许说成"她预算只够"。
- 退货不回仓（拆封的当周不再上架），所以 `stock` 只减，退货不补。
- 小样（`samples`）与现货是两个抽屉：`stock` 为 0 照样能试用，"迎上去"和派样发的都是小样，不被现货挡住。
- 两条出路 `transferStock`：罗曼走系统调拨单（`official`：+3 支、台账 +2、离柜 3 分钟，历史里写着名字）；唐可私下拿货（`tangke`：+3 支、台账 −9、人情 +8、离柜 2 分钟，系统里没这张单，且要 `relations.tangke >= TANGKE_STOCK_GATE = 45` 她才给）。一支一周一次（`transfer:<product>`），且只在剩到 `TRANSFER_GATE = 3` 以下才开口。`canTransfer` / `canTransferVia` / `transferLabel` 一处写、两个 UI 读。

### 界面（这一轮真正的分寸是"说几次"）

断货全场只说一次，说在报价单上（`柜上只剩 3 支，这单最多开到 3 件`）。连带按钮上那句"她不会多拿"在柜上空了时换成"柜上这一支断了"，两行调货只在 ≤3 支时出现在同一张报价单下面。没有库存面板、没有进度条、没有"剩余 N 支"的角标。

沙盘那一步量出一个真缺陷（截图里看见的，不是想出来的）：她开口三件、抽屉只剩两件时，`三件连带` 和 `四件整套` 两行都写着 `¥1,960`——分钟仍按开口的档位算，价钱按削完的件数算，玩家看不出自己少要了一件。改法是标签念成「N 件 ¥X」，规则没动（`minutes = BUNDLES[bundle].units` 这条时间契约原样保留）。手机版那两行调货最初用报价行的 flex 排，代价那句话被折成两列读不完，改成 `.order-quote > .stock-transfer` 的 grid（子选择器是必要的：`.order-quote > div` 压过 `.stock-transfer`）。同一屏还顺带量出成交那一排一直在折线以下，那是 P13。

### 红灯与返工（都留着，不改口）

- 配货上线后手机版 10 个用例一起红：`consequences.spec.ts`（8）和 `endings.spec.ts`（1）的手写存档没有 `stock`，`parseCampaign` 直接返回 null，"继续第 N 天"永远不出现——是存档校验在起作用，不是测试写坏了；`campaign.spec.ts`（1）钉着旧的 ¥25,590。夹具改成 `stock: { ...WEEK_ALLOCATION }`，数字照测出来的改。
- 两个界面的新用例第一版都在选连带之前就断言"只剩 N 支"：`bundle = "single"` 时 `wanted ≤ left`，那句本来不该出现。改成先按「三件整套」——也是玩家真实的操作顺序。
- 那两行调货一度"没到 44px"（28.14 / 23.42）：调试输出证明 `min-height: 44px` 已生效、`offsetHeight` 就是 44，是 Playwright 的 `boundingBox()` 按滚动容器裁掉了。契约改成 `offsetHeight ≥ 44` + 横向溢出 ≤1px + 真的点一次。
- 工具边界（本轮量出来，值得记下）：手机版 `npm run build` 的 `tsc` 只 `include: ["src"]`，`tests/` 与 `rescue-e2e/` 不在类型检查范围内，Playwright 只转译不检查类型。用项目同款开关单测这两个目录才发现我自己的 `stock-transfer.spec.ts` 有一处 `el.offsetHeight` 落在 `HTMLElement | SVGElement` 联合类型上（已改）。同一处扫描还看到一个先前就存在的 `rescue-e2e/counter.spec.ts:56`：把 `bundle` 当第 4 个参数传给只收 3 个参数的 `consult()`——行为没受影响（第 61 行按的还是同一个按钮），不是本轮引入的，先只记下没顺手改。

## P13 · 成交那一排一直在折线以下（P12 截图时撞出来的）

为什么动这一处：P12 要在沙盘上量断货那两行调货，截图时看见 `提出成交` 被裁掉半行。第一反应是"这一轮加的两行把它顶下去了"——量了才知道不是：把 `.stock-transfer` 整块摘掉，`提出成交` 的底边仍在 808，而视口只有 720。它在很久之前就在折线以下，跟这一轮没关系。

### 量出来的原状

- 1280×720：`.rescue-dock` 的 `scrollHeight 407 / clientHeight 299`——整条抽屉自己在滚；`提出成交` 底边 808，差 88px。
- 1440×900：底边 953 / 1013（差 53 / 113px），`scrollHeight 352 / 412` 对 `clientHeight 279`。
- 摘掉调货那两行，短空的像素一模一样 → 不是 P12 顶下去的。
- macOS 上滚动条默认不显示，这一屏没有任何"还能往下滚"的提示；而它长得像控制台，玩家不会想到去滚一个控制台。
- 为什么 e2e 一直是绿的：`counter.spec.ts` 每次都真的点 `提出成交`，而 `click()` 会先把元素滚进视野；`toBeVisible()` 走的是 `scrollIntoViewIfNeeded`，只保证"在滚动容器里"，不保证"在屏幕上"。这两个断言在这一屏上等于没测。

### 改法

`src/CounterGame.tsx` 把接待区拆成两层：`.service-actions` 占满整列，里面 `.service-body` 是唯一允许滚的一段，`.closing-buttons` 作为脚单独一格；`src/rescue.css` 里 `.rescue-dock` 由 `overflow: auto` 改成 `overflow: hidden`，`.dock-content` 不再滚。矮屏靠正文那段消化，没删文案、没缩字号。

第一版用的是 `position: sticky; bottom: 0`：`提出成交` 确实一直在屏幕上了，但那条带横切在连带按钮中间（截图上 `三件整套` 被盖掉一半，看得见、点不准）。撤回，改成分层。

### 契约：`rescue-e2e/dock-closing.spec.ts`（5 视口 × 2 分支 = 10 个用例）

不靠点击，只量位置：动作行底边 ≤ 视口高、`提出成交` 落在 dock 之内、`.rescue-dock` 与 `.dock-content` 都不许滚、`.service-body` 的 `overflow-y` 必须是 `auto`、滚到底时带顶与正文底之间不留负间隙，最后真点一次并核 `沈薇成交` 那张卡。拒绝那条分支（`换一款 / 留小样 / 接受拒绝 / 强推成交`，带子更高、正文被压得更矮）用同一个函数在 5 个视口各量一遍。

## P14 · 一周的货按天到：缺口咬在周中，"等"和"调"变成两个选项

为什么先动这一处：P12 自己在"仍未验证"里写着"配货是整周一份，没有每早到一批的节奏……空了只能调，不能等"。这一轮就是回去补那一条。另一个理由是 P12 的结论 3——约束太薄，整周只有第 5 天被削过一件，"这一单整个开不出来"那一屏要靠种子存档才见得到。同一份配货摊到五天，缺口就从周末挪到周中，那一屏变成正常玩法会撞上的事。

### 规则（只在 `campaign.ts`）

- `DELIVERIES` 五批：`[3,1,1] / [2,0,1] / [2,1,2] / [1,0,2] / [2,2,1]`（柔焦/持妆/修护）。逐支合计正好等于 `WEEK_ALLOCATION`（探针打的是 `配货=[10,4,7] 批次合计=[10,4,7]`），也就是"按天到"不新增一个单位的货，只改它什么时候在柜上。`FIRST_DAY_STOCK = DELIVERIES[0]`，`INITIAL.stock` 用它。
- 批次故意跟清洁路线的逐日动销错开两处：第 2 天柔焦差一支（¥980，便宜的缺口），第 4 天修护差一支（¥1,680，而且是安姐接住的同事需求）。便宜的用"等"就能补，贵的要人离柜三分钟去换——这才叫选择。
- `applyDawn` 在 `day > 1` 且没有 `delivered:<day>` 旗子时加当天那一批，旗子写进存档。探针：第 2 早 `[3,1,1] → [5,1,2]`，同一份再跑一次还是 `[5,1,2]`，重复过晨会不会双倍到货。
- `deliveryWord(day)` 一句念"今天到了什么 + 明天排的是什么"，第 5 天只念今天。晨会里 `speaker` 是「品牌 · 到货」，跟罗曼、唐可那两条走同一个流。探针：第 2 早念到到货的句子数 = 1，第 1 早也 = 1。第 1 天那句是「这一周的配货不是一次性给的：今天先出柔焦 3 支、持妆 1 支、修护 1 支，剩下的按天到。明天排的是柔焦 2 支、修护 1 支。」
- 调货闸门从"剩到 3 支以下就打"改成"这一单正被削件"：`offerTransfer = !risky && units < wanted && canTransfer`。`canTransfer` 里那条 `stock ≤ TRANSFER_GATE(3)` 保留着，所以两件事都成立才摆按钮——抽屉薄、而且她这一单正好开不满。`orderQuote` 为此多返回 `wanted`（她自己开口要的件数），两个 UI 一起读。
- `SAVE_VERSION` 5 → 6。字段没变，但 `stock` 的含义变了，见下面"红灯"第 4 条。
- "没买成"那张卡给的出路跟着排期变：这一支后面还排着批次才说"等大仓下一批补上"，第 5 天那种不会再补的改成"只剩两条路"。写死成"要么调拨要么找人"是 P12 的话，那时候确实只有两条。

### 界面

断货那一句仍然只在报价单上念一次，到货那一句仍然只在晨会念一次；没有库存面板、没有"剩余 N 支"的角标、没有到货提醒的第二处。手机版那句断货在 `.mobile-order-quote` 里，沙盘在 `.quote-note` 里，两行调货在两个界面都是 `.stock-transfer button`。

### 反事实：按天到到底从玩家手里拿走多少钱

同一副牌第 1 天一次性给满（`stock = WEEK_ALLOCATION` + 第 2–5 天的 `delivered` 旗子）跑同一条清洁路线 = **¥24,610、接到 10**；按天到 = **¥22,930、接到 9**。这条反事实钉在规则测试里（`tests/campaign-rules.test.ts`「按天到货真的咬在柜台上」），连同四件逐单核对：第 2 天周姐 1 件 vs 2 件、第 4 天周姐2 开不出来 vs 开得出来、第 5 天回来那位 4 件 vs 3 件。

差额 ¥1,680 不是一笔，是三段：第 2 天少开 1 件（−980）、第 4 天整单开不出来（−1,680）、第 5 天因为前面少花一支而多开 1 件（+980）。我第一版注释里写的"少 ¥1,680"是猜的，拆开才发现对不上，所以补了这条测试。

### 要撤回的一条结论（P12 结论 1）

P12 写的是：**"调货不是刷营业额的按钮。同一通电话在清洁路线上净亏 ¥700……两次电话里有一次是白花的。"** 新闸门下重测：清洁 + 罗曼 = **¥25,590、台账 91、接到 10、一个人没走**（比基准多 ¥2,660）；清洁 + 唐可 = **¥24,610**（多 ¥1,680，代价是台账 78、比基准低 8 分）。"净亏 ¥700"和"一次白花"都不成立，撤回。

原因是旧闸门看的是抽屉（≤3 支就打），模拟器因此会在柜台前没人被削件的时候离柜三分钟，队伍最后那位走了——那一步两个界面里都没有按钮可点，是模拟器自己造出来的时机。新闸门只在"这一单正被削"时摆按钮，省掉了那次白跑。

仍然成立的两条：全柜上脸 + 罗曼 = ¥22,230，在目标线上但只剩 ¥1,230 余量；硬开四件 + 罗曼 = ¥19,290，电话一次都没打出去（人先走了，她的单子从没被抽屉削过），这行按钮救不了推错产品的人。

### 新量到的一条："等"换不来钱，只换回节奏

第 1 天沈薇从 3 件改开 2 件（把那一支留给后天）：第 2 天周姐从 1 件变 2 件，五天总数还是 **¥22,930**、接到还是 9、余柔焦还是 0——省下来的那一支没有变成额外的钱，只是把同一支货挪到另一天卖。整周唯一能加出货的办法还是调货（+3 支，超出配货）。所以"等下一批"是排期与风险的杠杆（她当场等不等、柜位点不点名），不是营业额；这条只在模拟器里量过，没做过真人试玩。

### 红灯与返工（都留着，不改口）

- 手机版 `campaign.spec.ts` 严格模式炸了：`getByText('柜上这一支断了')` 命中 5 个元素（报价单那一句 + 四个连带按钮各印了一遍）。改成断言整句。
- 探针脚本挂到 180 秒超时（在 `page.locator(...).textContent()` 上等一个不出现的节点）。改成 `page.evaluate` 读 DOM + `actionTimeout`，跑完删掉。

### 本轮改掉的那一处，也是唯一一处会掉钱的

文案只在 `campaign.ts` 写一次，两个 UI 读：

### 改法（三处布局 + 一处字号，规则一个字没动）

2. 出现那一次把抽屉滚到它：`bundleRowShown` → `scrollIntoView({block:"nearest"})`，声明在原来的 `scrollTo({top:0})` 之后所以是它说了算；只滚挂载那一次，之后玩家自己滚的位置不再被覆盖。

### 量出来的三件事

1. **`max-height:46%` 一直夹着内联的 `height:48%`。** P16 记的"成交那一档抬到 48%、42% 会把提出成交顶到抽屉外"**从没渲染过**：实测抽屉高 45.8%，而 48% 那一档三枚面部线索离抽屉顶的屏幕像素 `(42,-2,4)` 与 46% 各档**完全一致**（真渲染了就该是 `(31,-13,-7)`）。修法是把 `max-height` 删掉，高度只由 `Prototype.tsx` 那一串阶段说一处 —— 而不是去调那个内联数字。
2. **脚是要还高度的**：单行 59 设计像素（1px 分隔线 + 6 + 44 + 8），拒绝那一档两行 102。成交档正文 516 → 464、可见带 390 → 328，净结果四格离脚 4 像素（不滚就在）。
3. **矮的那一档最先被脚吃掉**：观察档 17% 时她那句话被压在脚下 10 / 8 屏幕像素。试过 19%（只剩 1 像素贴线）→ 定 **20%**（余量 7 设计像素，因为自由输入那一档她的句子可能更长）。46% 那一档**没抬**：48% 会把脸颊、鼻翼盖进抽屉（-13 / -7），脸是主玩面；这两枚在 46% 已经各盖 2 / 1 像素，是既有代价，不是本轮新增。

### 契约怎么改（不是把红的改成绿的）

- `bundle-ask.spec.ts`：`overflow ≤ 1` 这个替身不再成立（脚底下的呼吸位也被它算进去），改成按几何量 —— 四格下沿 ≤ 脚的上沿、脚在 `.consultation-controls` 之外、脚整块在抽屉带内（`.consultation-dock` 是 `overflow:hidden`，掉出去不是"要滚"而是被裁）。12px 字号下限与"预算那句只念一遍"原样保留。

## P19 · 账本要能对回来：每笔动过 sales 的钱各写一行 ¥（2026-09-24）

结局屏的大数字 ¥22,930 和右边那份五日因果账本对不上：顺着账本往回加，加不出那个数。这一轮把"钱写在动它的那一行上"做成规则里的契约。**经济数值一个字没动。**

### 先分清两个"差"（第一轮我混过一次，如实记）

| 口径 | 清洁路线 | 私域路线 |
| --- | --- | --- |
| `sales` − Σ 账本上带 ¥ 的行（玩家看得见的差） | **1,680** | **8,960** |
| `sales` − Σ `orders.amount`（数据结构口径，不进小票的钱） | 980 | 8,260 |

开工时记的是"差 ¥980"，那是第二行的口径；玩家可见的是第一行。第二个差不该修 —— 私域补单和唐可转的单本来就没有收银小票。

**两处探针自身的问题也记着**：① 第一版审计器只认 ` · ¥`，旧代码的闭店调整写的是 `：−¥490`，于是把两条本来就带数额的行误报成本轮新增（改认两种写法后它们掉了出去）；② 上一轮 `/tmp` 探针把 `runRoute` 的 `dayTotals` 当成当日读，它是累计。

### 改的东西

- `campaign.ts` 新增 `receiptLine(text, amount)` 与 `ledgerSum(s)`：前者由规则在动 `sales` 的那一处调用（小票、闭店调整、退货冲回、小样回单、微信补单、晨会两笔私下成交、结局暂扣），后者反着读回去。
